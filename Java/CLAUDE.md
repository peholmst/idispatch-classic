# iDispatch Classic (Java)

Two products, each its own distribution unit with its own version and release tags (`RELEASING.md`, `release.sh`): `server/` (parent POM of `server/app`, the Spring Boot 4.1 + Vaadin 25.3 Flow app on Java 25, `server/aspsms-integration`, the generated SOAP client it uses, and `server/mobile`, the units' mobile app) and `runboard/` (standalone Swing client that receives dispatch notifications over the server's `/ws/runboard` WebSocket). `pom.xml` here only aggregates them; it is not a parent. CI is in `.github/workflows` at the repository root: `build.yml` on pull requests and `main`, `release.yml` on release tags. In this file, "the app" and paths under `server/app` mean the Vaadin application.

## Running and testing

- Run the app with the Vaadin dev loop, not `mvn spring-boot:run`: `server/app/.vaadin/vaadin-dev start`, then `apply` after edits. See the `vaadin-devloop` skill in `server/app/.claude/skills/`.
- App: http://localhost:8080/idispatch. Login is OIDC through Keycloak; dev users `admin` / `changeme` (all roles), `dispatcher` / `dispatcher`, `reports` / `reports` (reads reports), `reporter` / `reporter` (writes reports), `reviewer` / `reviewer` (closes and re-opens reports).
- Database is PostgreSQL from `server/app/compose.yaml`. Spring Boot's Docker Compose support starts it with the app and supplies the datasource; data persists in the `postgres-data` volume (`docker compose down -v` in `server/app/` wipes it). The Compose project is named `server`, as it was before the app moved to `server/app`, so its containers and volume are `server-*` and `server_postgres-data`.
- Keycloak (http://localhost:8180, admin console `admin` / `admin`) is in the same `compose.yaml` and imports the `idispatch` realm from `server/app/keycloak/idispatch-realm.json` when its container is created. Its data lives in the container and the import skips an existing realm, so a restart keeps the old realm: after editing the JSON file, run `docker compose up -d --force-recreate --wait keycloak` in `server/app/`, then log out of the app and back in, since roles are read at login. The app runs `docker compose up` on every start, bringing up whichever of PostgreSQL and Keycloak is missing, and leaves both running when it stops; `docker compose stop` in `server/app/` stops them. The app fails to start if Keycloak is down. Production setup: `server/docs/keycloak.md`.
- Schema changes go in a new Flyway migration in `server/app/src/main/resources/db/migration` (never edit an applied one).
- The server stores everything with jOOQ in Spring transactions; there is no JPA. The jOOQ metadata classes in `server/app/src/main/java/net/pkhapps/idispatch/server/jooq` are generated and checked in; never edit them. After adding a migration, regenerate them with `mvn -Pjooq-codegen -pl app -am generate-sources` in `server/`: it starts a throwaway PostgreSQL from `server/app/compose.jooq-codegen.yaml` (port 15432, no volume), runs the migrations, generates the classes and removes the database. `JooqTest` fails when they don't match the migrated schema. An `AssignmentReport` is a record of its `SceneDetails` and a `UnitReport` per responding unit, keyed by `ResourceId`, each remembering who last changed it (`UserStamp`); `AssignmentReport.withDraft` records an edit only on the parts whose content changed. The report service takes the version the user read, and refuses a closed report before it checks the version. `report/ReportForm` is a `RecordForm` with the scene, the counts and a section per unit; the rule that the casualties may not exceed the people involved is a form error under the people involved, and is also told in a notification when saving fails on it. A resource's current state is a `ResourceStatus` row, one per resource, and every change archives the state before it as an `ArchivedResourceStatus`, which the reports read through `ResourceQueries`. The rules for which states follow which, and when a resource is available or on its assignment, live on `ResourceStatus`; the `available` and `assigned` columns are written from them for querying. A `Destination` is a sealed type of `SmsDestination`, `RunboardDestination` and `MobileDestination` records, kept in the `dispatch` package because a sealed type's records must share its package; `sms` and `runboard` hold only the dispatchers. A `MobileDestination` has exactly one resource, and its app authenticates with a generated `MobileKey`, of which only the SHA-256 hash is stored: the service hands the key back only when it creates the destination or replaces the key, and the form shows it once as a QR code (`ui/QrCode`) of the pairing link `…/mobile/#pair=<key>`. Replacing the key doesn't change the destination's version. Dispatching stores a `DispatchNotification` record with the IDs of its resources and destinations, and publishes `DispatchNotificationSent` with the destinations as they were, which the dispatchers deliver; the runboard queue is in memory, keyed by destination ID, and an acknowledgement stores a `Receipt`. The reports list the closed assignments with a jOOQ query straight over the tables (`report/ClosedAssignmentQuery`), as flattened `ClosedAssignmentListItem`s.
- Production runs in Docker behind NGINX: `server/Dockerfile` (build context is `server/`, which holds everything the server needs; it builds with the app's `production` profile) and `server/deploy/compose.yaml`, documented in `server/docs/deployment.md`. Organisations deploy a checkout of an `idispatch-server/v<version>` tag. The drawer shows the version from Spring Boot's `build-info` (`BuildProperties`).
- `mvn -pl runboard -Passemble package` in this directory builds the runboard's installation zip, `runboard/target/iDispatchRunboard-<version>.zip`: the fat jar, launchers and voice download scripts for Windows (`.cmd`) and macOS/Linux (`.command`) from `runboard/src/main/dist`, and license texts. It needs Java 25 preinstalled. The release workflow attaches it to the runboard's GitHub Release.
- Run just the runboard against any server, such as production, with `runboard/run-local.sh` (settings in the Git-ignored `runboard/local/`; see `runboard/docs/speech.md`). Setting it up on a Raspberry Pi: `runboard/docs/raspberry-pi.md`.
- The mobile app (`server/mobile`, see its `README.md`) is a TypeScript + Lit + Vite app with Vaadin's web components in Aura, not Flow, as it has to work offline. Maven installs Node into its `target/`, runs `npm ci`, builds it into `target/classes/META-INF/resources/mobile` and runs its Vitest tests; the app depends on the module, so Spring serves the app under `/idispatch/mobile/` (Vaadin excludes `/mobile/**` and `/api/**`). Its API is `dispatch/mobile`, under `/idispatch/api/mobile/`, outside the Keycloak login: its own stateless security chain (`MobileSecurityConfig`) authenticates a request by the mobile destination key in `Authorization: Bearer` (`MobileKeyAuthenticationFilter`, which looks the destination up by the key's hash through `DestinationQueries`), and answers anything else with 401. The controller gets the `MobileDestination` as the principal, reads resources through `ResourceQueries`, and handles every exception itself, since Spring Boot's `/error` is behind the Keycloak login and would answer with a redirect. The app's only authority is `Roles.UNIT_PREFIX` + its resource ID (`UNIT_42`), which `ResourceStatusService.setResourceStateManually` accepts for that resource (`Roles.HAS_DISPATCHER_OR_IS_UNIT`); the unit sets the same states as the dispatcher's status dialog (`manualValidNextStates`). The app keeps `/api/mobile/events` open, a Server-Sent Events stream read with `fetch` (`MobileEventStreams`): a `unit` event on connecting and on every `ResourceStatusChanged` of its unit, sent in order on a thread of its own, and a heartbeat (`idispatch.mobile.heartbeat-interval`) that closes the stream once the destination is deleted or has a new key. The app's status buttons work only while the stream is open; nothing is queued. It colors the states with the server's `styles/dispatch-view-styles.css`, which it imports.
- Run Maven from `server/`, naming the app with `-pl app -am` when you want only it: the app depends on its sibling modules (`aspsms-integration`, `mobile`) at the same snapshot version, and run alone in `server/app/` Maven looks for them, and for the parent POM, in `~/.m2`, where they usually aren't.
- Tests: `mvn test` in `server/`; needs Docker, as `TestcontainersConfiguration` starts a PostgreSQL container per Spring context. Running Maven while the dev loop owns the app rewrites `target/classes` under it; run `.vaadin/vaadin-dev restart` afterwards.

## Conventions

- The server is packaged by feature: `municipality`, `assignmenttype`, `assignment`, `resource`, `dispatch` (with the delivery channels `dispatch/sms` and `dispatch/runboard`), `report`, `dispatcher` (the dispatcher's main view, and `ResourceStatusView` with a card per resource; both load their rows with `ResourceRows`) and `dashboard` (the home view). A feature package holds its records, repositories, services, events, views and a `*Formatters` class for its UI labels. Feature-neutral code lives in `shared` (`AbstractService`, `Bilingual`, `BilingualText`, `UpdateResult`), `shared/management` (`DefaultFilter`), `ui` (app shell, `RootLayout`, generic `Formatters`), `ui/management` (`RecordManagementView`, `RecordForm`) and `security`. Dependencies between features point one way: `municipality`, `assignmenttype` ← `assignment` ← `resource` ← `dispatch` ← `dispatcher`, with `report` on `assignment` and `resource`; `dashboard` reads the tables straight with jOOQ (`dashboard/DashboardQuery`) and depends on no feature. `ArchitectureTest` enforces this, and that `shared` and `security` know no feature and only `RootLayout` in `ui` does. When a feature needs something from one above it, it declares an interface that the feature above implements (`assignment/ResourcesOnAssignment`, implemented in `resource`). Services are plain Spring beans without interfaces (`AssignmentService`, `ResourceQueries`); an interface is only for such a dependency the other way. Every feature may use the generated `jooq` package. Test classes live in the package of the feature they test.
- Users and roles live only in Keycloak. Roles are the `idispatch` client roles `ADMIN`, `DISPATCHER`, `REPORT_READER`, `REPORT_WRITER`, `REPORT_REVIEWER`, read from the ID token's `roles` claim by `security/KeycloakRolesMapper` and mapped to the constants in `security/Roles`. Views use `@RolesAllowed`/`@PermitAll`, and layouts need an access annotation too. Services use `@Secured`; Spring Security reads it from the class that declares a method.
- The UI is in English, Swedish and Finnish. Texts come from `getTranslation(key)` (or `I18NProvider.translate` outside components) and live in `src/main/resources/vaadin-i18n/translations*.properties`; `translations.properties` is English, and every key must also be in `_sv` and `_fi`. There is no bean validation: records' domain primitives check themselves (`isValid`, and a constructor that refuses invalid values), and the forms show their own messages from `translations*.properties`. The language comes from the ID token's `locale` claim (`ui/UserLocale`), set on each UI when it is created; English is the fallback.
- `RootLayout` has no navbar. Each view puts a `ViewTitle` (drawer toggle and title) first in its own toolbar at the top of the view; `RecordManagementView` does this for all management views.
- Management views (under Administration in the drawer) extend `RecordManagementView`, a master-detail view (`MasterDetailLayout`) with the grid as master and a `RecordForm` subclass as detail, described with the records below. A view that adds more than one kind of record (the destinations) overrides `createAddButton` with a menu whose items call `startAdding(kind)`, and `createFormToAdd(kind)` and `getTitleToAdd(kind)`.
- An `Assignment` is filled in bit by bit, so nothing it holds is required; `Assignment.missingForDispatch()` is the rule for what dispatching needs, and `DispatchService` refuses an assignment that is not ready with `AssignmentNotReadyForDispatchException`. `DispatchView` follows MVVM: `DispatchViewModel` holds the open assignments, the selected one and all resources in signals, and creates `AssignmentViewModel` for the form; both are plain classes the view creates, testable with plain JUnit and Mockito (`*ViewModelTest`), and import nothing from Vaadin but signals. The panels only bind to them (`ui/SignalBindings.bindItems` for grids) and call their commands; the view subscribes to the services' events and tells the ViewModel through `OwnerUpdater`. Selecting an assignment is a command that opens it in the form. The form saves every change right away: the assignment is a signal, each field shows its part, and a change saves `assignment.with…(…)` and replaces the signal with the saved version (or with another dispatcher's newer one). Setting a combo box's items clears its value, so the form empties the assignment signal before it reloads the choices, or the clearing would be saved.
- Records are immutable, refer to other records by ID (`ResourceTypeId`), carry a `version` that an update checks (a stale one gets `OptimisticLockingFailureException`), and are built from domain primitives (`ResourceTypeCode`, `shared/BilingualText`). Grids and combo boxes get flattened list items (`ResourceTypeListItem`); editing loads the record by ID. Other features read a feature's records through its `*Queries` service (`MunicipalityQueries`, `AssignmentTypeQueries`), which is read-only and not secured, since it also serves dispatching in the background; the admin-only `*ManagementService` is for the management view. Their management views extend `RecordManagementView`, with a `RecordForm` as detail: each field is bound to a signal, the form derives each field's error from the primitives and creates the domain value (such as `ResourceTypeDetails`) only when every field is valid. Errors show once a field is touched or a save is tried, bound with `ui/SignalBindings.bindErrorMessage` (Vaadin has no signal binding for a field's error); fields that depend on each other share a touched signal. The form has changes while a field differs from its starting value, so changing a value back is no change. The view creates or updates the record from that value through the feature's service.
- Services publish Spring application events, kept in the package of the feature that publishes them, synchronously. A view that refreshes on an event must go through `OwnerUpdater`, which locks the right session, makes the view's UI and session current, and runs as the view's owner. The UI must be current because local signals refuse access from another session, and an effect runs right away only when its own UI is current. Server push is enabled.
- Theme is Aura (dark), loaded with `@StyleSheet` on `AppShellConfiguratorImpl` together with `META-INF/resources/styles.css`, which sets the app-wide density and `@import`s the per-area stylesheets in `META-INF/resources/styles/`. Put new CSS there, not in `src/main/frontend` with `@CssImport`. Use the theme-neutral variants (`ButtonVariant.PRIMARY`, not `LUMO_*`/`AURA_*`) and `--vaadin-*`/`--aura-*` properties, never `--lumo-*`. Style Grid cells with part name generators and `::part()`, not `themeFor`.
- Use the Vaadin docs MCP server for Vaadin 25.3 APIs rather than recalled Vaadin 24 knowledge.
- The runboard reads notifications out loud through the speech engine SPI in `runboard/.../speech` (Piper is the only engine). Engine code stays behind that SPI; see `runboard/docs/speech.md`.
- The runboard switches the amplifier and the flashing light through the output driver SPI in `runboard/.../output`: `none` (default, desktops) or `gpio` (Linux GPIO character device through FFM, for the Raspberry Pi); see `runboard/docs/outputs.md`.

## Tests

- Spring Boot tests import `TestSecurityConfiguration`, which replaces the Keycloak client registration so the context starts without Keycloak. Service tests authenticate with `@WithMockUser`.
- UI tests are browserless use-case tests that extend `ui/UseCaseTest`: one test per use case, named after it, written in the verbs of an actor (`Dispatcher`, `Administrator`, `ReportUser`) that works in its own user and window from the secured browserless application context (`user(...)`, `keycloakUser(...)`, `visitor()`). Actors use page objects (`AppShell`, `DispatcherPage`, `AdministrationPage`, `ReportsPage`), the only place that knows labels and components; they read grids as cell texts by column header through `GridRows`. Find things the way the user does (label, text, `setAriaLabel` for icon-only controls), never through view classes. They are the harness for refactoring the UI: change page objects, not stories, when the layout changes.
- Services use `REQUIRES_NEW` transactions, so nothing rolls back: set up the starting situation with `TestData` (and `report/HandledAssignments` for closed assignments) and unique names. All `UseCaseTest` classes share one Spring context; keep their `@Import` identical.
- `TestData` writes and reads the database with jOOQ and returns its own records (`GivenResource`, `GivenMunicipality`, …), so it does not change when a feature's records or repositories do. Fixtures that need the secured services call them through `ui/RunAs`.
- Component queries only find visible components, components behind a modal dialog can't be used or read through testers, and exceptions from click listeners reach the test instead of the session error handler.
- The browserless application holds every session's lock, so multi-user stories (`TwoDispatchersTest`) cannot catch unlocked cross-session UI access (vaadin/browserless-test#295), and `OwnerUpdater` updates another session's view directly, with that view's UI made current.
