# iDispatch Classic (Java)

Maven reactor: `server` (Spring Boot 4.1 + Vaadin 25.3 Flow app, Java 25), `aspsms-integration` (generated SOAP client used by `server`), `runboard` (standalone Swing client that receives dispatch notifications over the server's `/ws/runboard` WebSocket).

## Running and testing

- Run the app with the Vaadin dev loop, not `mvn spring-boot:run`: `server/.vaadin/vaadin-dev start`, then `apply` after edits. See the `vaadin-devloop` skill in `server/.claude/skills/`.
- App: http://localhost:8080/idispatch. Login is OIDC through Keycloak; dev users `admin` / `changeme` (all roles), `dispatcher` / `dispatcher`, `reports` / `reports` (reads reports), `reporter` / `reporter` (writes reports), `reviewer` / `reviewer` (closes and re-opens reports).
- Database is PostgreSQL from `server/compose.yaml`. Spring Boot's Docker Compose support starts it with the app and supplies the datasource; data persists in the `postgres-data` volume (`docker compose down -v` in `server/` wipes it).
- Keycloak (http://localhost:8180, admin console `admin` / `admin`) is in the same `compose.yaml` and imports the `idispatch` realm from `server/keycloak/idispatch-realm.json` when its container is created. Its data lives in the container and the import skips an existing realm, so a restart keeps the old realm: after editing the JSON file, run `docker compose up -d --force-recreate --wait keycloak` in `server/`, then log out of the app and back in, since roles are read at login. The app runs `docker compose up` on every start, bringing up whichever of PostgreSQL and Keycloak is missing, and leaves both running when it stops; `docker compose stop` in `server/` stops them. The app fails to start if Keycloak is down. Production setup: `server/docs/keycloak.md`.
- Schema changes go in a new Flyway migration in `server/src/main/resources/db/migration` (never edit an applied one). Hibernate runs with `ddl-auto: validate`, so the app fails to start if the entities and the schema disagree.
- The server is moving from JPA to jOOQ feature by feature; both run side by side on the same data source and Spring transactions. The jOOQ metadata classes in `server/src/main/java/net/pkhapps/idispatch/server/jooq` are generated and checked in; never edit them. After adding a migration, regenerate them with `mvn -Pjooq-codegen generate-sources` in `server/`: it starts a throwaway PostgreSQL from `server/compose.jooq-codegen.yaml` (port 15432, no volume), runs the migrations, generates the classes and removes the database. `JooqTest` fails when they don't match the migrated schema. Moved so far: resource types, assignment types, municipalities and assignments. The JPA entities that refer to them do so by ID: `Resource` by `typeId` (with read-only `@Formula` columns for the type's description until resources move too), `ResourceStatus`, `ArchivedResourceStatus`, `DispatchNotification` and `AssignmentReport` by `assignmentId`, and `DispatchNotification` also by `assignmentTypeId` and `municipalityId`, whose names the dispatchers look up when they send. Everything else refers to resources by `ResourceId` too: `ResourceStatus`, `ArchivedResourceStatus`, `Destination`, `DispatchNotification` and the unit reports in `AssignmentReport` store the ID, `ResourceStatusService` and `DispatchService` take it, and the call signs come from `ResourceQueries` (a jOOQ query over the `resources` table returning `ResourceListItem`s). The reports list the closed assignments with a jOOQ query straight over the tables (`report/ClosedAssignmentQuery`), as flattened `ClosedAssignmentListItem`s.
- Production runs in Docker behind NGINX: `server/Dockerfile` (build context is this directory) and `server/deploy/compose.yaml`, documented in `server/docs/deployment.md`.
- `mvn -pl runboard -Passemble package` builds the runboard's installation zip, `runboard/target/iDispatchRunboard-<version>.zip`: the fat jar, launchers and voice download scripts for Windows (`.cmd`) and macOS/Linux (`.command`) from `runboard/src/main/dist`, and license texts. It needs Java 25 preinstalled.
- Run just the runboard against any server, such as production, with `runboard/run-local.sh` (settings in the Git-ignored `runboard/local/`; see `runboard/docs/speech.md`). Setting it up on a Raspberry Pi: `runboard/docs/raspberry-pi.md`.
- Tests: `mvn test` in `server/`; needs Docker, as `TestcontainersConfiguration` starts a PostgreSQL container per Spring context. Running Maven while the dev loop owns the app rewrites `target/classes` under it; run `.vaadin/vaadin-dev restart` afterwards.

## Conventions

- The server is packaged by feature: `municipality`, `assignmenttype`, `assignment`, `resource`, `dispatch` (with the delivery channels `dispatch/sms` and `dispatch/runboard`), `report` and `workstation` (the dispatcher's main view). A feature package holds its entities, repositories, `*Specifications`, services, events, views and a `*Formatters` class for its UI labels. Feature-neutral code lives in `shared` (entity and service base classes, `Bilingual`, `ValidationFailedException`, `UpdateResult`), `shared/management` (management service base classes), `ui` (app shell, `RootLayout`, generic `Formatters`), `ui/management` (management view and form base classes) and `security`. Dependencies between features point one way: `municipality`, `assignmenttype` ← `assignment` ← `resource` ← `dispatch` ← `workstation`, with `report` on `assignment` and `resource`. `ArchitectureTest` enforces this, and that `shared` and `security` know no feature and only `RootLayout` in `ui` does. When a feature needs something from one above it, it declares an interface that the feature above implements (`assignment/ResourcesOnAssignment`, implemented in `resource`). Every feature may use the generated `jooq` package. Test classes live in the package of the feature they test.
- Users and roles live only in Keycloak. Roles are the `idispatch` client roles `ADMIN`, `DISPATCHER`, `REPORT_READER`, `REPORT_WRITER`, `REPORT_REVIEWER`, read from the ID token's `roles` claim by `security/KeycloakRolesMapper` and mapped to the constants in `security/Roles`. Views use `@RolesAllowed`/`@PermitAll`, and layouts need an access annotation too. Services use `@Secured`; Spring Security reads it from the class that declares a method, so methods inherited from `AbstractManagementServiceBean` are secured there.
- The UI is in English, Swedish and Finnish. Texts come from `getTranslation(key)` (or `I18NProvider.translate` outside components) and live in `src/main/resources/vaadin-i18n/translations*.properties`; `translations.properties` is English, and every key must also be in `_sv` and `_fi`. Bean validation messages are `{idispatch.…}` keys in `ValidationMessages*.properties`, shown through `ValidationFailedException.getViolationMessages(locale)`; only the JPA entities still use them. Records moved to jOOQ have no bean validation: their domain primitives check themselves (`isValid`, and a constructor that refuses invalid values), and the forms show their own messages from `translations*.properties`. The language comes from the ID token's `locale` claim (`ui/UserLocale`), set on each UI when it is created; English is the fallback.
- `RootLayout` has no navbar. Each view puts a `ViewTitle` (drawer toggle and title) first in its own toolbar at the top of the view; `AbstractManagementView` does this for all management views.
- Management views (under Administration in the drawer) extend `AbstractManagementView`, a master-detail view (`MasterDetailLayout`) with the grid as master and a `ManagementForm` subclass as detail. The edited entity is held in a signal; forms use a buffered `BeanValidationBinder` bound by property name, so the entity's bean validation constraints show next to the fields, and write to a copy of the entity on save. Filtering goes through `DefaultFilter` and a `*Specifications` class per entity.
- An `Assignment` is filled in bit by bit, so nothing it holds is required; `Assignment.missingForDispatch()` is the rule for what dispatching needs, and `DispatchService` refuses an assignment that is not ready with `AssignmentNotReadyForDispatchException`. The workstation's assignment form saves every change right away: the assignment is a signal, each field shows its part, and a change saves `assignment.with…(…)` and replaces the signal with the saved version (or with another dispatcher's newer one). Setting a combo box's items clears its value, so the form empties the assignment signal before it reloads the choices, or the clearing would be saved.
- Records moved to jOOQ are immutable, refer to other records by ID (`ResourceTypeId`), carry a `version` that an update checks (a stale one gets `OptimisticLockingFailureException`), and are built from domain primitives (`ResourceTypeCode`, `shared/BilingualText`). Grids and combo boxes get flattened list items (`ResourceTypeListItem`); editing loads the record by ID. Other features read a feature's records through its `*Queries` interface (`MunicipalityQueries`, `AssignmentTypeQueries`), which is read-only and not secured, since it also serves dispatching in the background; the admin-only `*ManagementService` is for the management view. Their management views extend `RecordManagementView`, which looks and works like `AbstractManagementView`, with a `RecordForm` as detail: each field is bound to a signal, the form derives each field's error from the primitives and creates the domain value (such as `ResourceTypeDetails`) only when every field is valid. Errors show once a field is touched or a save is tried, bound with `ui/SignalBindings.bindErrorMessage` (Vaadin has no signal binding for a field's error); fields that depend on each other share a touched signal. The form has changes while a field differs from its starting value, so changing a value back is no change. The view creates or updates the record from that value through the feature's service.
- Services publish Spring application events, kept in the package of the feature that publishes them, synchronously. A view that refreshes on an event must go through `OwnerUpdater`, which locks the right session and runs as the view's owner. Server push is enabled.
- Theme is Aura (dark), loaded with `@StyleSheet` on `AppShellConfiguratorImpl` together with `META-INF/resources/styles.css`, which sets the app-wide density and `@import`s the per-area stylesheets in `META-INF/resources/styles/`. Put new CSS there, not in `src/main/frontend` with `@CssImport`. Use the theme-neutral variants (`ButtonVariant.PRIMARY`, not `LUMO_*`/`AURA_*`) and `--vaadin-*`/`--aura-*` properties, never `--lumo-*`. Style Grid cells with part name generators and `::part()`, not `themeFor`.
- Use the Vaadin docs MCP server for Vaadin 25.3 APIs rather than recalled Vaadin 24 knowledge.
- The runboard reads notifications out loud through the speech engine SPI in `runboard/.../speech` (Piper is the only engine). Engine code stays behind that SPI; see `runboard/docs/speech.md`.

## Tests

- Spring Boot tests import `TestSecurityConfiguration`, which replaces the Keycloak client registration so the context starts without Keycloak. Service tests authenticate with `@WithMockUser`.
- UI tests are browserless use-case tests that extend `ui/UseCaseTest`: one test per use case, named after it, written in the verbs of an actor (`Dispatcher`, `Administrator`, `ReportUser`) that works in its own user and window from the secured browserless application context (`user(...)`, `keycloakUser(...)`, `visitor()`). Actors use page objects (`AppShell`, `DispatcherPage`, `AdministrationPage`, `ReportsPage`), the only place that knows labels and components; they read grids as cell texts by column header through `GridRows`. Find things the way the user does (label, text, `setAriaLabel` for icon-only controls), never through view classes. They are the harness for refactoring the UI: change page objects, not stories, when the layout changes.
- Services use `REQUIRES_NEW` transactions, so nothing rolls back: set up the starting situation with `TestData` (and `report/HandledAssignments` for closed assignments) and unique names. All `UseCaseTest` classes share one Spring context; keep their `@Import` identical.
- `TestData` writes and reads the database with jOOQ and returns its own records (`GivenResource`, `GivenMunicipality`, …), not entities, so it survives a feature's move from JPA to jOOQ. Fixtures that need the secured services call them through `ui/RunAs`.
- Component queries only find visible components, components behind a modal dialog can't be used or read through testers, and exceptions from click listeners reach the test instead of the session error handler.
- The browserless application holds every session's lock, so multi-user stories (`TwoDispatchersTest`) cannot catch unlocked cross-session UI access (vaadin/browserless-test#295), and `OwnerUpdater` updates another session's view directly; a story in which two dispatchers both have an assignment open fails on the form's signals for that reason, not because of an app bug.
